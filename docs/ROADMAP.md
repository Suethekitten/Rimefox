## 1. 定位与原则

凛狐（Rimefox）是一个**自建 API 的浏览器双语对照翻译扩展**：不接第三方免费端点，不收集用户内容，零构建（纯原生 JS）。

排序原则：

1. **先修问题，再加功能** —— 翻译错位、重复、丢格式这类问题优先于新入口
2. **不引入构建步骤** —— 保持"改完文件重载即可"，降低协作门槛
3. **每个改动配回归测试** —— `selftest` 是唯一能离线验证的防线
4. **明确不做的事写在最后** —— 避免路线图无限膨胀

## 4. 版本与发布节奏

- 版本号同步两处：`manifest.json` 与 `content/core.js` 的 `DT.VERSION`
- 推送到 main 且改动了 `manifest.json` 时，CI 自动：校验版本 → 跑离线自检 → 打包 `Rimefox-v<版本>.zip` → 从 CHANGELOG 摘说明 → 建 Release
- **纯文档 / 纯重构提交不升版本**，避免触发发版
- 每个版本在 `CHANGELOG.md` 补一段，写清"为什么改"

## 5. 改代码前的最低要求

1. 动 `content/dom.js`（切分 / 注入）→ 先跑 `selftest/index.html`（37 条，离线）
2. 新增"跳过规则"→ 想清楚会不会把**可见内容**跳过（弹层、下拉菜单常被 `opacity` / `aria-hidden` 标记）
3. 新增"替换规则"→ 想清楚会不会把**正文**替换掉
4. 新增入口（划词 / 悬停 / 输入框）→ 复用现有 `translate` 消息与缓存，不要另起请求链路

## 6. 如何提议新功能

在 Issue 里写清三件事：

1. **什么场景**（在哪个站点、什么操作下）
2. **现在会怎样**（截图或诊断 JSON：弹窗「诊断」按钮可复制）
3. **期望怎样**

有诊断 JSON 的问题通常一轮就能定位；没有的话往往要多轮追问。
